# Phase 3 — Production hardening runbook

**Do not execute Release-mode steps in this document on development or bench
boards.** Release-mode eFuse burns are irreversible and per-device: UART
download and JTAG/USB-debug are permanently disabled, so a mis-burned unit
cannot be recovered — it is scrap. Use a **dedicated, disposable production
unit** for every burn, never the board you iterate on day to day.

This is the gate procedure for the first commercial production run, after
Phase 2 hardware validation (`docs/secure-bringup.md` P2-5) is signed off on
at least one prototype of the **exact chip family being manufactured**.

Upstream: `docs/hardware-security-hardening-plan.md`,
`docs/phase2-encryption-spec.md`.

---

## 0. Chip-family prerequisite (read this first)

Every ESP32-family target in `hardware-targets.json` except `esp8266-uart-lite`
now has an `idf` / `idf-secure` / `idf-secureboot` build (see
`platformio.ini` and `docs/secure-bringup.md`'s build table) and all of them
build under `scripts/run-checks.sh` (`esp32-c6-4mb`'s trio in an isolated
PlatformIO core directory). `esp8266-uart-lite` cannot participate in any of
this — ESP8266 is a different chip family with no ESP-IDF, no flash
encryption, and no Secure Boot v2 concept; Phase 3 is structurally an
ESP32-family-only story.

**Build tooling existing is not the same as P2-5 being signed off.** The
functional checklist in `docs/secure-bringup.md` has to be run for real, on
a physical prototype, **per chip family you intend to manufacture** — a
passing classic-ESP32 run says nothing about S3, C3, S2, C6, or the 8 MB
board. None of these have been hardware-validated yet. `idf-c6` in
particular is the least proven build in this repo (community platform fork,
never confirmed outside CI) — do not treat a green CI run there as
equivalent to a real-hardware pass.

Silicon-security notes differ by family:

| | Classic ESP32 (LX6) | ESP32-S3 (LX7) |
|---|---|---|
| Secure Boot v2 chip-revision gate | **ECO3+ only** (`CONFIG_ESP32_REV_MIN_3`) — many `esp32dev` modules in the wild are older revisions; check silicon before committing to a SKU | No revision gate — Secure Boot v2 + flash encryption supported on all S3 revisions |
| Debug interfaces to lock down | UART download mode only | UART download mode **and** the native USB-OTG/USB-JTAG peripheral — burn `DIS_USB_JTAG` (or equivalent eFuse for the IDF version in use) in addition to the UART-download disable, or the built-in USB debug port bypasses the UART lockout entirely |
| espefuse chip check | `espefuse.py summary` → confirm `WAFER_VERSION`/`revision` ≥ 3 | `espefuse.py summary` → confirm chip identifies as genuine ESP32-S3, no revision gate needed |

Run `esptool.py --port <PORT> chip_id` and `espefuse.py --port <PORT> summary`
on every new hardware batch as an incoming-inspection step, independent of
per-unit production — this confirms the SKU matches what the signed image and
partition table assume before a single unit goes down the line.

## 1. Preconditions (must all be true before burning a single Release-mode fuse)

- [ ] P2-5 functional checklist (`docs/secure-bringup.md`) passed on ≥1
      prototype of the **exact chip family/revision** being manufactured,
      using `idf-secure`
- [ ] P2-5 Secure Boot item passed with `idf-secureboot` on that same
      family (unsigned image rejected) — ECO3+ prototype if classic ESP32
- [ ] OTA check-and-apply verified end-to-end on an encrypted, secure-booted
      unit, including anti-rollback rejecting an older signed floor
- [ ] Production Secure Boot signing keypair generated, escrowed (§2), and
      **distinct** from the OTA metadata ECDSA key (`OTA_SIGNING_PRIVATE_KEY_B64`)
      and from any `keys/*.pem` dev key
- [ ] Manufacturing fixture/station built: can flash, run the functional
      smoke test, burn eFuses, print the claim-code label, and log the result
      per unit (§4–§6)
- [ ] Written recovery/DOA policy signed off (§7) — expect and budget for
      scrap
- [ ] A named operator (§3) trained on this runbook, not improvising live on
      the first production batch

## 2. Key ceremony

Two keys are involved and they are **not interchangeable**:

| Key | Scheme | Generated by | Lives where | Purpose |
|---|---|---|---|---|
| Flash-encryption key | AES-256 | **The chip itself**, on first boot in Development mode (already how `idf-secure` behaves today) | Inside eFuse, never leaves the chip, unreadable once Release mode is burned | Encrypts flash contents (app + NVS) at rest |
| Secure Boot v2 signing key | RSA-3072 (matches `scripts/generate-secure-boot-dev-key.sh`'s scheme — `espsecure.py generate_signing_key --version 2 --scheme rsa3072`) | **You, once**, offline, before the first production run | Private half: offline/escrowed, never on a CI runner. Public digest: burned into every unit's eFuse at flash time | Only images signed by this key boot |

This resolves the plan's "key-provisioning choice": there is nothing to
decide for the flash-encryption key — device-generated is both the
recommendation and already the shipped Phase 2 behavior, no action needed.
The Secure Boot key is not a per-device choice at all; it is one company
keypair, generated once, reused (never rotated per-unit) across the whole
production run until a deliberate key rotation.

### Generating the production Secure Boot key

```bash
python3 espsecure.py generate_signing_key --version 2 --scheme rsa3072 \
  jkbmsr-secureboot-prod-<YYYYMMDD>.pem
```

- Generate on an **offline** machine, ideally one that never touches the
  network again afterward (or is wiped after).
- Do **not** store this the way `OTA_SIGNING_PRIVATE_KEY_B64` is handled —
  that pattern is fine for the OTA key because a leaked OTA key only lets
  an attacker sign a *firmware update*
  (still gated by the device accepting it, and revocable by rotating the key
  and shipping a patch). A leaked Secure Boot key means an attacker can
  produce a boot chain your hardware will trust **permanently** for every
  unit ever burned with its matching public digest — there is no remote
  rotation path for units already in the field. Keep it on offline media
  (encrypted USB key in a safe, or split via `openssl` / Shamir's Secret
  Sharing across ≥2 people if you want M-of-N recovery) and only load it onto
  the manufacturing station's signing step, air-gapped from the internet.
- Never derive it from, or reuse it as, the OTA metadata key or any
  `keys/*.pem` dev key — a compromise of one must not compromise the other.
- Record the key's fingerprint (`openssl rsa -in <key>.pem -pubout | openssl
  sha256`) in a durable, offline location (not just this repo) so a burned
  unit's digest can be verified against it later if provenance is ever
  disputed.

## 3. Roles

At this scale (bench/low-volume manufacturing, not a contracted EMS line),
one trained operator is enough — do not over-build process for a run of
single-digit-to-low-hundreds of units. Recommended minimum:

- **Operator**: runs the station, follows §5 exactly, signs off each unit's
  log line.
- **Key holder** (can be the same person, but should not be *only* one
  person for the escrow copy — see §2): has offline access to the Secure
  Boot private key for re-signing a new image if a bug is found before
  Release-mode burns begin. Once units are burned, the key is only needed
  again for the *next* firmware build, not to un-burn anything.

## 4. Station requirements

- Host machine (or Pi) with PlatformIO / `esptool.py` / `espsecure.py` /
  `espefuse.py` installed, same versions used to validate P2-5.
- UART programming jig for the target board (pogo-pin fixture or USB cable,
  matching however dev boards are currently flashed).
- The **signed** production firmware image (built from the `idf-secureboot`
  successor env for the target chip family — see §0 if that's not classic
  ESP32).
- Label printer capable of printing the device ID + a claim-code QR
  (`https://jkbmsr.com/onboard?device=<id>&code=<code>` — same URL shape
  `CaptivePortal::buildOnboardUrl()` already generates; the label just needs
  to reproduce it, no new endpoint required).
- A simple per-unit log (spreadsheet/CSV is fine at this volume — device ID,
  timestamp, operator, firmware version, pass/fail per step, final
  disposition). This is your warranty/traceability record; keep it durably,
  it outlives any single burned unit.

## 5. Production flow (per unit)

Ordering matters: **every functional test happens before the irreversible
burn**, never after. Burning first and testing second turns every failure
into scrap instead of a re-flashable retry.

1. **Incoming check.** `esptool.py chip_id` + `espefuse.py summary` — confirm
   chip family/revision matches the signed image's target (§0). Reject
   mismatches before flashing anything.
2. **Flash.** Write the signed bootloader + app + partition table over UART.
   The unit is still in Development mode at this point — fully re-flashable,
   nothing burned yet.
3. **First boot / self-encrypt.** Power on. The bootloader generates the
   flash-encryption key into eFuse, encrypts flash in place, and resets —
   same behavior already validated in P2-5. Wait for the second boot to
   complete.
4. **Functional smoke test** (station fixture, same shape as the P2-5
   checklist, run against *this specific unit*):
   - [ ] Boots to provisioning (empty NVS)
   - [ ] Station provisions WiFi (fixture AP or wired-equivalent) and the
         device connects
   - [ ] Device mints device ID + claim code, registers with the cloud
   - [ ] One telemetry sample uploads successfully over TLS
   - [ ] OTA check endpoint reachable and returns a valid (even if
         no-op/current) response
   - [ ] `esptool.py read_flash` of the NVS region returns ciphertext, not
         plaintext SSID/password
   
   **Any failure here → do not proceed to step 6. Diagnose or scrap while
   still re-flashable.**
5. **Label.** Print device ID + claim-code QR from the values already
   persisted in step 3–4. Do this before sealing so a failed unit at step 4
   never gets a label printed for it.
6. **Seal (Release mode — irreversible, only after 4 passes).** Burn the
   remaining Release-mode eFuses per the Espressif Secure Boot v2 + flash
   encryption workflow for the target chip:
   - Disable UART download mode.
   - Classic ESP32: nothing else chip-specific.
     ESP32-S3: also disable the native USB-OTG/USB-JTAG debug path (§0) —
     skipping this leaves a live debug interface Release mode on classic
     ESP32 doesn't have to worry about.
   - Lock `FLASH_CRYPT_CNT` (prevents further re-encryption cycles).
   - Confirm the Secure Boot public-key digest is burned and matches §2's
     production key fingerprint.
7. **Post-burn negative test (100%, not sampled — it's cheap and
   non-destructive).** Attempt a UART download command against the sealed
   unit; confirm it is rejected. This is the only proof the burn actually
   took — don't skip it to save time.
8. **Log.** Record device ID, firmware version, operator, timestamps for
   steps 2/6, and pass/fail for every checkbox above, in the station log
   (§4). This line is what makes a field warranty claim or an audit possible
   later.
9. **Pack.**

---

## 6. QA sampling

Do not sample-test before the burn (step 4) — it's an irreversible step, so
every unit gets the full functional test, not a subset. The post-burn
negative test (step 7) is also 100%: it costs one UART command and doesn't
touch the unit's state, so there's no volume-driven reason to sample it
either. Sampling only makes sense for **destructive** or highly
time-expensive tests (e.g., a full extended burn-in soak) if those get added
later — nothing in this runbook currently qualifies.

---

## 7. Recovery / DOA policy

- **Before step 6 (not yet sealed):** any failure is a re-flash-and-retry.
  Diagnose, don't scrap prematurely.
- **After step 6 (sealed):** UART download and JTAG/USB-debug are gone.
  Recovery is only possible via signed OTA, and only if the unit can still
  boot and reach the network. A unit that fails to boot, or that fails the
  step-7 negative test in the wrong direction (i.e., burn didn't take),
  cannot be field-recovered — it is scrap. Budget scrap into unit economics;
  do not treat a bad burn as an emergency to "fix" via any UART/JTAG
  workaround — there isn't one, and reduces confidence that Release mode is
  doing what it claims.

---

## Explicit non-goals here

- Retrofitting encryption onto field units already shipped without Phase 2
  firmware — physical re-flash + eFuse burn only, no OTA path exists for
  this by design (flash encryption is not something OTA can enable after the
  fact).
- Replacing the OTA ECDSA metadata-signing process — separate key, already
  live, untouched by this runbook.
- Improv-over-BLE — still deferred, unrelated to Phase 3.
